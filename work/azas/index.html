서비스 소개

부모와 자녀가 가족 관계를 연결하고 자산·거래 기록을 함께 확인하는 가족 자산관리 서비스입니다. 내부 모의 이체, 가족 초대, 알림과 리포트를 통해 금융 활동을 관리합니다.

실제 은행 송금이 아닌 서비스 내부 모의 거래입니다. 담당 범위는 이체·알림·가족 초대·리포트 연계와 계좌 정보·토큰 보호입니다.

사용 흐름

  1. 1초대 수락으로 가족 관계 연결
  2. 2계좌·자산 및 거래 기록 확인
  3. 3내부 모의 이체 요청
  4. 4거래내역·알림·리포트 확인

기술 구성과 역할

Java · Spring
이체, 가족 초대, 알림과 리포트의 백엔드 업무 로직을 구현했습니다. 이체의 잔액·거래내역·상태 변경을 같은 트랜잭션에서 처리합니다.
MyBatis · MySQL
SQL 기반 데이터 접근과 저장을 담당합니다. 멱등키 UNIQUE 제약, 계좌 잠금, 잔액 조건부 차감과 알림 복합 인덱스를 적용했습니다.
k6
조회 중심 부하 실험에 사용했습니다. 폴링 주기별 API 응답시간과 HTTP 실패율을 비교했습니다.

담당 기능 및 구현 과정

상황

화면에서 중복 클릭을 막아도 네트워크 재전송·동시 출금·처리 중 예외가 발생할 수 있었습니다.

과제

모의 이체가 중복 실행되거나 잔액과 거래내역 일부만 반영되지 않도록 서버와 DB에서 처리해야 했습니다.

실행

내부 모의 이체

재전송과 중복 요청을 구분하기 위해 UUID 멱등키와 DB UNIQUE 제약을 적용했습니다. 동시에 같은 계좌를 다루는 요청은 계좌 ID 순서로 비관적 락을 획득하도록 했습니다. 잔액 조건부 차감과 거래내역·상태 변경을 한 트랜잭션에 묶어 성공 시 함께 반영하고 실패 시 함께 롤백하도록 구현했습니다.

알림 조회

이미 조회한 알림 이후의 데이터만 가져오도록 after_id 기반 Keyset Pagination을 적용하고 조회 조건에 맞는 복합 인덱스를 구성했습니다. k6에서 5·10·15초 폴링 조건을 비교하며 API 응답시간과 HTTP 실패율을 확인했습니다.

가족 초대

한 자녀를 참조하던 초대를 가족 단위로 확장했습니다. 초대를 발급할 때 활성 자녀 목록을 고정하고, 수락할 때 그 목록의 자녀를 일괄 연결하도록 변경했습니다. 발급 이후 가족 구성이 바뀌어도 초대 대상이 임의로 달라지지 않도록 발급 시점을 기준으로 삼았습니다.

계좌 정보 및 토큰 보호

다시 표시해야 하는 계좌번호는 AES-256-GCM으로 암호화하고 조회용 해시를 별도로 두었습니다. 일치 여부를 확인하는 초대 토큰과 Refresh Token은 해시로 저장했으며, Refresh Token 회전을 적용했습니다.

리포트 갱신 연계

이체 처리에 리포트 갱신을 연결했습니다. 현재 구현은 같은 트랜잭션에 포함되므로 리포트 갱신 실패도 이체 롤백에 영향을 줍니다. 이체와 부가 집계의 처리 책임을 분리할 지점으로 확인했습니다.

설계 판단

1. 잠금 순서와 트랜잭션 경계

동시 이체가 서로 다른 순서로 계좌를 잠그지 않도록 계좌 ID 순서를 고정했습니다. 잔액과 거래내역을 함께 반영하기 위해 트랜잭션 범위를 묶었습니다.

2. 암호화와 해시 구분

복원이 필요한 계좌번호와 일치 여부만 확인할 토큰의 사용 목적을 구분했습니다. 각각 암호화와 해시 저장을 적용했습니다.

3. 초대 대상의 기준 시점

초대 수락 전 가족 구성이 바뀌는 상황을 고려해 발급 시 활성 자녀 목록을 고정했습니다.
