서비스 소개

금융 사기 관련 질문에 공식 문서의 근거를 연결하는 RAG 서비스입니다. 문서를 임베딩해 검색하고, 질문에 필요한 자료를 답변 생성에 연결합니다.

기록된 고도화는 AI 구현 지원을 활용한 증분 임베딩·재처리 실험입니다. 수치 결과는 합성 데이터와 모의 임베딩 공급자를 이용한 조건별 실험입니다.

사용 흐름

  1. 1공식 문서 수집·청크 구성
  2. 2임베딩 생성 및 벡터 저장
  3. 3사용자 질문과 관련된 문서 검색
  4. 4검색 근거를 활용한 답변 제공

기술 구성과 역할

Spring Boot
웹 서비스의 API와 AI 처리 모듈을 연결하는 백엔드 계층입니다.
FastAPI
RAG의 임베딩·검색 처리를 웹 API로 연결하는 AI 처리 계층입니다.
PostgreSQL · pgvector
문서 벡터의 저장과 검색에 사용했습니다. 본문 변경과 모델 설정을 기준으로 벡터의 재사용 여부를 판단합니다.

주요 기능의 처리 순서 · 구현 설명용 도식

  4. 4

담당 기능 및 구현 과정

상황

문서 일부만 변경돼도 전체를 재임베딩했고, 새로 발급되는 청크 ID만으로는 기존 벡터를 재사용하기 어려웠습니다.

과제

AI 구현 지원을 활용해 변경 입력만 처리하고 실패 후 완료된 배치를 재사용하는 흐름을 구성했습니다.

실행

증분 임베딩 처리

공식 문서를 검색하는 RAG 처리 과정에서 일부 내용이 바뀌어도 전체 문서를 다시 임베딩하는 작업을 줄이고자 했습니다. AI 구현 지원을 받아 본문 해시와 임베딩 모델 설정을 재사용 기준으로 구성했습니다. 같은 내용과 설정의 벡터는 재사용하고 변경된 입력만 새로 처리하도록 했습니다.

배치 실패 후 재처리

완료된 배치의 캐시와 검색에 사용할 활성 인덱스를 구분했습니다. 일부 배치가 실패한 뒤 다시 실행할 때, 이미 성공한 입력은 캐시에서 재사용하고 나머지 입력을 처리하는 흐름을 구성했습니다.

변경 조건별 비교 실험

합성 청크, 모의 임베딩 공급자와 실제 pgvector를 이용해 변경 없음·일부 변경·전체 변경·실패 후 재실행을 비교했습니다. 재생성 입력 수와 배치 호출 수를 확인해 변경량에 따라 재사용이 적용되는지 점검했습니다.

결과

모의 임베딩 공급자를 사용한 실험에서 100청크 중 10개 변경 시 재생성 입력은 100개에서 10개, 배치 호출은 4회에서 1회로 줄었습니다. 65개 입력의 실패 후 재실행에서는 완료된 32개를 재사용하고 33개를 처리했습니다. 변경이 없으면 신규 호출은 0회, 전체 변경 시에는 100개를 처리하는 결과를 확인했습니다.

설계 판단

1. 캐시 키 구성

청크 ID가 재발급되는 경우를 고려해 본문 해시와 모델 설정으로 재사용 여부를 판단했습니다. 같은 본문이라도 모델 설정이 바뀌면 다시 처리하도록 했습니다.

2. 캐시와 활성 인덱스 분리

성공한 배치를 재사용하는 것과 검색에 공개할 데이터를 결정하는 것을 구분했습니다. 실패 후 재실행 시 완료된 작업을 반복하지 않도록 고려했습니다.
